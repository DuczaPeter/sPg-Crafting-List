## 4. Material inventory model

The canonical material batch builder is `buildCanonicalMaterialBatchRecord()`.

Current batch fields:

- stable batch ID: `id`, generated by `makeId("batch")` and preserved on edit;
- canonical material identity: `materialUuid`;
- display label: `materialName`;
- provenance identity when different: optional `sourceMaterialUuid`;
- integer Quality: `quality`, nullable, valid range 0–1000;
- quantity: safe integer `quantityUnits`;
- unit: `SCU` or `ITEM`;
- optional `note`;
- `createdAt`, `updatedAt`.

`toScuUnits()` converts SCU input with `Math.round(number * 10000)` and `fromScuUnits()` divides by 10000. `normalizeBlueprint()` stores SCU recipe quantities with the same scale. The UI explicitly states the model, and allocation rejects non-integer `quantityUnits`. This proves the current representation: **1 SCU = 10 000 internal units**.

The existing rounding converter is an ingestion compatibility path and must not be called by Craft Complete. Completion arithmetic must use only already validated integer `requiredQuantityUnits × completedQuantity`, with `Number.isSafeInteger` checks and zero rounding.

Flows:

- add/edit: `saveMaterialBatchFromForm()` → `buildCanonicalMaterialBatchRecord()` → `persistMaterialBatches()`;
- delete: `deleteMaterialBatch()` → `persistMaterialBatches()`;
- persistence: `UserDataRepository.saveMaterialBatches()` → `commitInventorySnapshot()`;
- reload: `restoreUserDataState()` → `loadMaterialBatches()`;
- grouping: `buildMaterialInventoryGroups()` uses the exact canonical lookup, then groups by `canonical UUID + unit` while retaining source UUIDs and individual batches.

No fuzzy or name-only merge is used for canonical grouping. Legacy source UUID can remain provenance, while new records are written under the resolved canonical UUID.

## 5. Allocation and reservation model

The allocation entry point is `allocateCardsDeterministically(cards, batches, materialQualityPlans, canonicalMaterials, materialQualityPools)`.

Current behavior proven from code:

- active cards are sorted by persisted `order`, then `id`; this is Crafting Card priority;
- batches are normalized and initially sorted by `createdAt`, then `id` through `compareStableIdentity()`;
- within an eligible Quality rule, `compareEligibleBatches()` selects highest Quality first only for `HIGHEST_Q`; minimum/target rules select the lowest eligible Quality first, with stable identity as tie-breaker;
- same-card requirements sharing canonical material and unit are scheduled by stricter effective minimum first, then stable slot order;
- `evaluateRequirement()` walks the eligible batch array in order and pushes `{batchId, quality, allocatedUnits, reason}`. It never proportionally mixes batches;
- a shared `remaining` map prevents physical batch double reservation across slots and cards;
- Minimum pool is `[minimumQ, maximumQ)` and MAX pool is `[maximumQ, +infinity)`; invalid or missing thresholds fail safe;
- shortage is split into `missingAmountUnits` and `missingQualityUnits` and propagated with explicit status;
- `maxCraftable` uses integer whole-item simulation; requested card quantity is a positive integer.

There is **no explicit persisted reservation object**. The current reservation exists only in memory under:

- `state.allocationResult.cards[].requirements[].allocatedBatches` for per-card/per-slot lines;
- `state.allocationResult.trace[]` for ordered evidence;
- `state.allocationResult.batchUsage[]` for global per-batch reserved totals.

`recalculateAllocation()` rebuilds that in-memory result after local mutations. Reload reconstructs it from stored cards and batches. There is no partial completion, consumption, Craft History, revision counter or stale-reservation check in V003.

### Exact partial consumption from the visible reservation

For a chosen whole output quantity `N`, each recipe slot needs exactly:

`requiredUnits = requirement.requiredQuantityUnits × N`

The operation must walk that slot's already visible `allocatedBatches` in allocation order and consume a prefix until `requiredUnits` reaches zero. It must not spread the amount proportionally, run allocation again, use a fallback batch, or change Quality.

`MAX` for completion must be the largest whole quantity supported by the **current visible reservation**, capped by the card's remaining quantity. It is the minimum, across recipe slots, of `floor(sum(reserved allocation units for slot) / per-item units)`. This deliberately does not use completion-time reallocation. If any multiplication is unsafe/non-integer, or the visible lines cannot cover every slot exactly, completion is `BLOCKED` with zero writes.

### Deterministic `reservationSnapshotHash`

Create a canonical JSON payload with schema marker `V004_RESERVATION_SNAPSHOT_1`. Object keys are sorted, but semantic arrays preserve Allocation Engine order. The payload contains:

- `craftingCardId`, `cardRevision`, `craftListRevision`, `inventoryRevision`, `allocationRevision`;
- persisted card priority/order, remaining card quantity, blueprint/item IDs and active SC data version;
- for every recipe slot: `allocationSequence`, slot ID, ingredient UUID, canonical material UUID, unit, integer per-item units, required/reserved units, exact Quality rule/pool assignment, threshold and range status;
- for every reserved line, in existing order: line sequence, `batchId`, canonical and source material UUID, unit, Quality, batch `quantityUnits` at snapshot time, reserved `allocatedUnits` and allocation reason.

Hash the UTF-8 canonical JSON with SHA-256 and store the lowercase hexadecimal result. If Web Crypto SHA-256 is unavailable in the runtime, snapshot creation and completion are blocked; no weak fallback hash is allowed for this safety boundary.

Before any write, the completion transaction validates **all** reserved entries from the snapshot, including entries not consumed by a partial completion. Missing batch, insufficient units, changed identity/provenance/unit/Quality/quantity, changed card/revision/list revision, changed allocation revision or changed inventory revision produces `STALE_RESERVATION` and aborts the whole transaction. Explicit reallocation is then required.

## 6. Crafting Card model

`buildCraftingCard()` creates the persisted model. Current fields include:

- `id`, `order`, `active`, `collapsed`, `quantity`;
- `blueprintUuid`, `blueprintCacheKey`, `gameVersion`;
- `outputUuid`, `outputName`, `outputType`, `outputTypeLabel`;
- blueprint/output links, crafting time and availability;
- sanitized `requirements[]` with stable recipe slot IDs, ingredient/canonical bridge fields, integer `requiredQuantityUnits`, unit and Quality capability;
- `slotStrategies` and `recipeSlotQualityPoolAssignments`;
- timestamps.

Create/update/delete flow:

- create: `buildCraftingCard()` through `addCurrentBlueprintCard()` or `addC010FinalCardToCraftingList()`;
- update: `updateCraftingCard()` and the strategy/pool/quantity callbacks;
- reorder: `moveCraftingCard()`;
- duplicate: `duplicateCraftingCard()`;
- delete: `deleteCraftingCard()`;
- storage: `persistCraftingCards()` → `UserDataRepository.saveCraftingCards()` → `commitCraftingCardsSnapshot()`;
- render: `renderCraftingCards()` → shared `buildFinalCraftingCardViewModel()` and `renderFinalCraftingCardContent()`.

The save path rewrites `order` and `updatedAt` for every card. Therefore `updatedAt` cannot safely stand in for `cardRevision`.

Smallest-risk additions:

- `cardRevision`: persisted on each card; increment only for allocation-relevant changes to that card. Collapse-only presentation changes do not invalidate it.
- `craftListRevision`: `userMeta` counter incremented for add/delete/duplicate/reorder and full-card restore.
- Craft Complete controls: add to the `renderCraftingCards()` management/action area, using the existing shared card result and a dedicated confirmation/control block; do not place the action on the transient Blueprint Browser preview.
- partial quantity: a committed integer input local to the completion control, default `1`, plus `MAX`; it does not overwrite the card's remaining `quantity` before the atomic commit.
- `Aktív Craftok | Craft History`: add an internal subview controller inside `craftingCardsPanel`. No sidebar/navigation module is added.

The normalized blueprint/card model does **not** retain an explicit recipe output-count field. It currently treats card quantity as the direct multiplier of per-item requirements and labels it in finished-item `DB`. Before implementation, C002 must map and test an exact API output-count source if recipes can output more than one item per craft. Absence of a proven source must block those recipes rather than guess.

## 7. Backup and import model

Current backup schema 2 serializes five arrays through `M4_BACKUP_STORE_SPECS`: `userInventory`, `materialBatches`, `craftingCards`, `miningLoadouts`, `userSettings`.

- serializer: `buildM4BackupEnvelope()`;
- parser/migration: `validateAndMigrateM4Backup()`;
- current backward compatibility: schema 1 → schema 2;
- record validation: `validateM4UserData()`;
- read-only preview: `buildM4ImportPreview()` plus pre/post fingerprint assertion;
- apply: explicit `window.confirm`, pre-import snapshot, then `commitUserDataImport()`;
- current fingerprint: canonicalized data with a 32-bit FNV-style hash.

V004 backup schema 3 must add `craftHistory` and the required durable `userMeta` subset. V003 schema 1/2 backups remain accepted by V004 and are transformed as follows:

- preserve all existing supported V003 User Data records;
- add `craftHistory: []`;
- initialize revisions deterministically;
- record the V003 source fingerprint and migration metadata;
- mark all runtime reservation snapshots absent/stale until V004 explicitly allocates.

V004 schema 3 backups are intentionally rejected by V003's current parser because V003 accepts only schema 1–2. That is the required one-way compatibility boundary.

Craft History is append-only during V004 import. Identical transaction IDs may be treated as unchanged; conflicting records block the entire import. `REPLACE` must not delete local history. Revision metadata is recomputed/advanced after import rather than blindly trusting imported counters. This keeps History and Undo data through backup/restore without creating stale valid reservations.

### Direct V003 database migration

1. User opens V004 and explicitly chooses V003 migration.
2. V004 proves that source database `spg-crafting-list` version 4 and required stores exist, then reads the five V003 User Data stores in one `readonly` transaction.
3. V004 builds and offers a V003 backup download before enabling the final migration confirmation.
4. Canonical source data plus source database/schema metadata is SHA-256 fingerprinted.
5. Migration is allowed only into a pristine V004 User Data target.
6. One V004 write transaction inserts converted User Data, empty history, initialized revisions and a successful migration ledger record.
7. Same fingerprint again: `V003_MIGRATION_ALREADY_APPLIED`, `BLOCKED`.
8. A different V003 fingerprint after a successful migration: `V003_SOURCE_CHANGED_AFTER_MIGRATION`, `BLOCKED`; first-version automatic merge is forbidden.

The V003 database receives no put/delete/clear/version-change request.

## 8. Multi-window current state

The V003 source contains no `BroadcastChannel`, `storage` event listener, `navigator.locks` use or application-level cross-tab synchronization. `sessionStorage` is used only for bounded session logs. `AppDatabase.open()` closes its connection on `versionchange`.

Current IndexedDB transactions rely on browser transaction scheduling for their declared store scopes. The application does not prove a stronger cross-window business isolation guarantee, does not compare user-data revisions inside writes and does not serialize a read-modify-write operation across tabs.

V004 plan:

- `userMeta.inventoryRevision`: increment in the same transaction as every material-batch mutation, Craft Complete, Undo and import/migration.
- per-card `cardRevision`: increment with allocation-relevant card content changes.
- `userMeta.craftListRevision`: increment with list membership/order changes.
- `userMeta.allocationRevision`: increment whenever allocation inputs change and when the user explicitly accepts a fresh reallocation.
- primary notification: `BroadcastChannel("spg-crafting-list-v004-sync")` after a committed mutation;
- fallback: on `focus` and `visibilitychange`, re-read revision metadata. Do not assume file-origin `storage` events are reliable.

A receiving tab marks its visible reservation snapshots stale and shows an explicit notification plus Reallocate action. It does not silently recalculate a snapshot into a completion-ready state. Correctness comes from revision and exact-batch validation inside the atomic transaction; the channel is only a prompt UI optimization.

## 10. Implementation blockers / architecture mismatches

Proven mismatches which C002–C003 must resolve:

- no separate V004 database or migration ledger;
- no `craftHistory` or `userMeta` store;
- no persisted revision counters or per-card revision;
- no explicit persisted reservation and no current snapshot hash;
- no cross-tab state notification;
- existing inventory and card writes are separate snapshot transactions;
- `AppDatabase.request()` resolves before transaction completion and is unsuitable as the atomic completion boundary;
- card `updatedAt` is rewritten for all cards by snapshot save and cannot be a concurrency token;
- backup schema 2 omits history/revision metadata;
- the current 32-bit backup fingerprint is not sufficient as the V003 migration idempotency key;
- the existing SCU ingestion helper rounds and must not be reused in completion arithmetic;
- no explicit recipe output-count field is retained by normalization.

These are bounded additions/refactors with identified insertion points. No contradiction was found that prevents a safe implementation plan.

## 11. Proposed schema additions

### `craftingCards`

- `cardRevision` positive safe integer.
- Existing `quantity` becomes explicitly the remaining finished-item count.

### `userMeta` store, key path `key`

- `inventoryRevision`;
- `craftListRevision`;
- `allocationRevision`;
- `historySequence`;
- migration record `migration:v003` with source fingerprint, source schema/db version, timestamp and status.

### `craftHistory` store, key path `craftTransactionId`

Required event fields:

- `craftTransactionId`, `historySequence`, `craftingCardId`;
- blueprint/item ID, item name;
- completed quantity, remaining before, remaining after;
- `inventoryRevisionBefore/After`, `cardRevisionBefore/After`, `craftListRevisionBefore/After`, `allocationRevision`;
- `reservationSnapshotHash` and snapshot schema;
- exact consumed material/batch/Quality/unit deltas in reservation order;
- timestamp, `status: COMPLETED | UNDONE`, undo timestamp;
- pre-craft Card snapshot;
- undo inventory revisions and restored-batch metadata when applicable.

Recommended indexes: compound card/sequence index for latest-only Undo and sequence index for newest-first rendering. `craftTransactionId` uniqueness plus `objectStore.add()` provides the idempotency constraint.

### Atomic Craft Complete

One read-write transaction covers `materialBatches`, `userInventory`, `craftingCards`, `craftHistory`, `userMeta`:

1. reject duplicate transaction ID;
2. read and validate revision records, card and every reserved batch snapshot entry;
3. derive exact prefix deltas for the chosen whole quantity without reallocation or rounding;
4. deduct each exact batch delta, never below zero; delete a fully consumed batch rather than retain a visible zero batch;
5. update the derived `userInventory` aggregates;
6. add the immutable History event;
7. decrement card quantity and increment card revision, or remove the fully completed card and increment list revision;
8. increment inventory/allocation revisions;
9. resolve only on transaction completion; any error aborts all stores.

### Atomic Undo

The same store scope validates status and latest-only rules. Partial Undo requires the current card revision to equal the event's post-completion revision. Full-card Undo requires the current craft-list revision to equal the event's post-completion list revision. Inventory may otherwise have changed.

Exact deltas return to the original batch only when the current record is compatible in canonical/source UUID, unit, Quality and protected content. Otherwise create a deterministic restored batch linked to the original batch and transaction; never overwrite an incompatible record. Update history to `UNDONE`, restore/decrement card state and advance revisions in the same transaction. Redo is absent.

## 13. Future targeted tests

1. `EXACT_BATCH_CONSERVATION`: for every touched batch, `before = consumed + after`; allowed delta is 0 unit.
2. `SMALL_REMAINDER_PRESERVED`: a deduction leaves a one-unit remainder and proves it is not rounded away or deleted.
3. `PARTIAL_21_TO_16`: completing 5 finished items from a card quantity of 21 leaves exactly 16 and records 5.
4. `FULL_CARD_REMOVAL`: completing the full remaining quantity removes the active card and creates one History event.
5. `RESERVATION_PREFIX_ORDER`: multi-batch consumption follows the visible Allocation Engine line order; no proportional mix, fallback or Quality replacement.
6. `NON_INTEGER_OR_UNSAFE_REQUIREMENT_BLOCKED`: any non-exact internal-unit result is `BLOCKED` with zero writes.
7. `STALE_RESERVED_ENTRY_BLOCKED`: missing, insufficient or changed reserved batch entry blocks all writes.
8. `ATOMIC_FAILURE_ROLLBACK`: injected failure after tentative deductions leaves inventory, card, revisions and History unchanged.
9. `CRAFT_TRANSACTION_IDEMPOTENCY`: replaying the same transaction ID causes only one deduction and one event.
10. `SECOND_STALE_TRANSACTION_BLOCKED`: two tabs start from one snapshot; the first commits, the second is blocked by revisions and batch checks.
11. `UNDO_EXACT_DELTA_RESTORE`: restores exact consumed units without replacing unrelated inventory state; compatible and restored-batch paths both pass.
12. `UNDO_LATEST_ONLY`: only the latest active `COMPLETED` event for a card can be undone; an event can be undone once; no Redo.
13. `HISTORY_UNDO_BACKUP_ROUNDTRIP`: History status, deltas, revisions and Undo eligibility survive V004 export/import.
14. `V003_TO_V004_MIGRATION`: V003 batches/cards/loadouts/settings are preserved, V004 history starts empty, V003 source fingerprint is stored and V003 DB bytes/state are unchanged.
15. `MIGRATION_REPLAY_AND_CHANGED_SOURCE_BLOCKED`: same fingerprint and later changed V003 source are both blocked without merge.
16. `OUTPUT_COUNT_MAPPING`: exact API output-count mapping produces whole finished-item semantics; missing/unproven or non-divisible data blocks completion.
